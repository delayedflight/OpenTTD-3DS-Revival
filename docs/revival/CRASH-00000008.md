# Crash 00000008 — preliminary graphics-queue diagnosis

Analysed 7 November 2026. User confirms **r3p**, 256x256 map, ordinary play
before getting a chance to save. This is not evidence of a save-operation crash.
No application code, build behaviour, device data or original save was changed.

## Verified evidence

The read-only copied dump is 508 bytes, SHA256
762a926cab382a572cd79fe53d6fe6e1ede389b03e14944e6d6e5eebc546e0e7.
Local raw evidence is under work/crash-dumps/00000008 (outside canonical Git).
The Luma parser reports ARM11 core0, prefetch abort, svcBreak panic/debug event.
PC=0x002e2970, LR=0x002da3a4. Using the preserved r3p ELF, PC resolves to
svcBreak and LR to gxCmdQueueClear. Disassembly immediately before LR calls
svcBreak(0) after checking current queue equality and a running flag. This is
an intentional library panic, rather than a direct invalid-memory-access report.

All96 captured instruction bytes match r3p ELF at 0x002e2914; r3q does not match
there. This corroborates the user's build identification; it is not a complete
hash of the crashed executable. The preserved r3p executable hash is
51005f76866194a04ae5ed5a249263782e8d63ca0a012b4bb1d291c9d527d332.
The executable currently on SD hashes to r3q and thus cannot identify the earlier
crashed binary. Current boot/audio logs were copied only as later-state evidence.

Stack words resolve to C3Di_WaitAndClearQueue, N3DS_FlipHWSurface, SDL_UpdateRect,
DrawSurfaceToScreen and VideoDriver_SDL::MainLoop. They support a display-update
path but are candidate returns, not a debugger-unwound complete call stack.
Other plausible-looking words, including a malloc address, cannot establish OOM.

## Source explanation and remaining uncertainty

libctru2.7.0 gxCmdQueueClear panics when its queue is the currently running queue:
https://raw.githubusercontent.com/devkitPro/libctru/v2.7.0/libctru/source/gpu/gxqueue.c
Citro3D1.7.1 WaitAndClear first waits, then stops/clears that queue:
https://raw.githubusercontent.com/devkitPro/citro3d/v1.7.1/source/renderqueue.c

The actual installed SDL1.2.15-19 package recipe uses a 3DS patch. Our preserved
patch SHA256 matches its published recipe:
83941419c8fc87a280b1d45db595b720fe190959a0094c727a566d2b9de20804.
Patch source:
https://raw.githubusercontent.com/devkitPro/pacman-packages/master/3ds/SDL/SDL-1.2.15.patch
Package recipe:
https://raw.githubusercontent.com/devkitPro/pacman-packages/master/3ds/SDL/PKGBUILD

In that patch, drawBuffers performs C3D_SyncDisplayTransfer/texture setup on the
calling thread and signals a private video thread. The video thread separately
calls C3D_FrameBegin/Draw/End. These paths share Citro3D state; the inspected paths
have no explicit mutual-exclusion/finished-frame handshake around those operations.
This makes overlapping transfer/render queue access a concrete race candidate,
consistent with the panic condition. The dump alone cannot prove the interleaving
or exclude corruption/other causes. There is no measured memory exhaustion here.

The OpenTTD code calls SDL_UpdateRect for display presentation. The SDK graphics
path remains present in r3q; its train interface changes do not establish a fix.
This failure is distinct from the earlier AI/pool crash and from cached-scroll
pixel corruption. Emulator success does not rule out hardware scheduling races.

## Next repair investigation

1. Verify the exact linked backend assembly and reproduce/force transfer-render
   overlap with a deterministic concurrency harness before choosing the patch.
2. Establish one owner, or explicit safe handoff, for Citro3D queue/texture access
   across SDL's transfer and renderer paths. A lock only around the application's
   SDL_UpdateRect call does not by itself lock the internal rendering thread.
3. Do not suppress svcBreak or rely on a delay/FPS limit as the correctness fix.
   Preserve texture-buffer lifetime, shutdown and app-suspend/GPU-right handling.
4. Build an isolated diagnostic repair with exact ELF; test both screen modes,
   scrolling, menus, train pairing, music/effects and repeated save/load; obtain
   sustained original-3DS results. Keep r3p/r3q binaries and tags unchanged.
5. Measure heap headroom separately; smaller maps may reduce load but cannot be
   certified safe or called the remedy from this dump.

No fix or reproduction is claimed yet. Newest evidence and this next-step plan
are recorded in STATUS.md for continuing in a fresh session if desired.
